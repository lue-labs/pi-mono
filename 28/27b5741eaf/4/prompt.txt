--- README.md
# pi-workflow

Deterministic JavaScript workflow orchestrator for pi. Clones Claude Code's `Workflow` (`RunWorkflow`) tool, built on top of pi-mono-fork's `ctx.forkAgent`. Conformance against the **current** CLI is tracked in [CC-2.1.153.md](./CC-2.1.153.md).

**Phase 1 (this commit):** inline scripts only, sync execution, single-agent + parallel + pipeline primitives. See [DESIGN.md](./DESIGN.md) for the full multi-phase roadmap.

## What it does

Lets the agent execute a sandboxed JS script that orchestrates one or many subagents. The script runs with `Date.now()` / `Math.random()` / timers shimmed to throw — so any run can be replayed deterministically from a journal (phase 4).

Every script (inline `script` included) must begin with an AST-validated pure-literal
`export const meta = { name, description, phases }` header, and `script` is the
current param name (`code` is accepted as a deprecated 2.1.146 alias). Metadata
may use only object/array/scalar literals; spreads, computed keys, methods/accessors,
function calls, and invalid `name`/`description`/`phases` are rejected cleanly.

```ts
// Example inline workflow
Workflow({
  args: "What's the carbon footprint of a transatlantic flight?",
  script: `
    export const meta = { name: "footprint", description: "cited research answer", phases: [{ title: "Scope" }, { title: "Search" }, { title: "Synthesize" }] };
    phase("Scope");
    const angles = await agent(
      \`Decompose the question into 4 search angles: \${args}\`,
      { schema: { type: "object", properties: { angles: { type: "array", items: { type: "string" } } } } },
    );

    phase("Search");
    const findings = await pipeline(
      angles.angles,
      angle => agent(\`Research: \${angle}\`, { label: \`research \${angle}\`, model: "fast" }),
      finding => agent(\`Verify and tighten citations:\\n\${finding}\`, { label: "verify", model: "medium" }),
    );

    phase("Synthesize");
    return await agent(\`Synthesize a cited answer from these findings:\\n\${findings.join("\\n---\\n")}\`);
  `,
})
```

## Globals available inside scripts

| Global | Type | Notes |
|---|---|---|
| `args` | `unknown` | Whatever you passed as `args`. |
| `cwd` | `string` | Deterministic workflow working directory. |
| `process.cwd()` | `() => string` | Deterministic shim returning the same value as `cwd`. No other `process` APIs are exposed. |
| `log(msg)` | `(string) => void` | Emits to the workflow's log feed (capped at 1000 lines). |
| `phase(title)` | `(string) => void` | Marks a progress group. **Marker only — takes a title, runs no callback.** Put work at top level after the marker: `phase("audit"); const x = await parallel([() => agent("…")]); phase("synthesize")`. Never write `phase("audit", async () => { … })`; it throws because the callback would never run, silently producing a 0-agent no-op. |
| `budget` | `{ total, spent(), remaining() }` | Token budget. `total` defaults to 128000 (CC's `task_budget` default); `spent()` meters real tokens from each subagent run. Scripts self-limit via `budget.remaining()`. |
| `agent(prompt, opts?)` | `(string, opts) => Promise<string|object>` | Spawns one subagent via `ctx.forkAgent`. |
| `parallel(tasks)` | `(() => Promise<T>)[] => Promise<T[]>` | Concurrent fan-out, default concurrency = `min(16, cores - 2)`. |
| `pipeline(items, ...stages)` | `(T[], ...fns) => Promise<R[]>` | Fan-out pipeline: each item moves through stages sequentially while items run concurrently. |
| `pipeline(stages)` | `(() => Promise<T>)[] => Promise<T[]>` | Back-compat sequential thunk-array form. |
| `workflow(name|{scriptPath}, args?)` | nested call | **Phase 5** — currently throws. |

### `agent()` options

```ts
agent(prompt, {
  label?: string,           // shown in UI
  schema?: object,          // JSON Schema → forces JSON return (parsed from text in MVP)
  model?: string,           // tier alias ("fast"/"medium") or id; defaults to parent's model
  allowedTools?: string[],  // restrict child's tool surface
})
```

**Accepted call shapes.** `agent()` coerces the shapes authors reach for, so
none of these silently drop the prompt:

```ts
agent("prompt", { label, model, agent: "explore" })   // the contract
agent({ task: "prompt", description: "label", extraContext: "…", agent: "explore" })  // object form
agent("explore", "prompt", { model })                  // agentType-FIRST ordering
```

`task`/`prompt`/`text` → prompt, `extraContext` folds into the prompt,
`description` → `label`, and `agent`/`subagent_type`/`agentType` → `opts.agentType`.

> **Cache note.** Every subagent forks with a byte-identical system prompt
> (`WORKFLOW_SUBAGENT_SYSTEM`) and `context: "none"`, so the parent's mutable
> prompt (cwd/date/skills/transcript) never bleeds in. All workflow subagents
> across every session and cwd share one warm Anthropic cache entry. See the
> `pi-cache-stability` skill. Subagent output is uncapped, 1:1 with Claude Code
> (which does not cap workflow subagents).
>
> **Optimisation inheritance.** Children inherit the optimised fork runtime
> automatically — resolved model (parent snapshot → Opus 4.8 and any future
> default), adaptive thinking (model metadata), and thinking level. Only an
> explicit `opts.model` overrides; model/thinking are never hard-set, so
> subagents track future fork tuning instead of freezing at today's values.
>
> **Progress metadata.** Completed agent rows read provider/model/thinking from
> `AgentToolDetails.runs[0]`, the truthful fork result. Running rows only know
> explicit `opts.model`; provider and thinking show `pending` until the fork
> reports. If a completed run record lacks provider/thinking, the UI shows
> `unavailable` rather than inventing values.

### Determinism

These are unavailable inside scripts — they throw `DeterminismViolation` with the original Claude Code rationale:

- `Date.now()`, `new Date()`, `Date()`, `Date.parse()`, `Date.UTC()`
- `Math.random()`
- `setTimeout`, `setInterval`, `setImmediate`, `queueMicrotask`
- `fetch`, `require`

If you need timestamps, stamp them after the workflow returns or pass them via `args`.

## Running dynamic workflows

Inline (dynamic) scripts run as soon as the model invokes the `Workflow` tool.
There is no extra "Run dynamic workflow?" confirmation prompt; the user's query
is the permission. To stop a foreground run already underway, interrupt the turn
(Esc).

| Env | Effect |
| --- | --- |
| `PI_DISABLE_WORKFLOWS=1` | Disable the Workflow tool entirely. |

## Persistence

Progress rendering groups agent rows by the active `phase(title)` marker. Each
phase header shows counts for `running`, `done`, `error`, and `skipped` (journal
replay). Large fan-outs keep the flat/tree signal readable by showing the newest
rows per phase plus an omitted-earlier count.

Every run writes to `${cwd}/.pi/workflows/runs/<runId>/`:

- `script.js` — the inline source (phase 3 will accept this back as `scriptPath`).
- `meta.json` — status + summary + result artifact metadata.
- `result.json` / `result.md` / `result.txt` — the full workflow return value.

The model-facing tool result stays compact: completion text includes a short preview, artifact path, format, character count, approximate token count, headings/top-level index, and instructions to inspect the artifact with `Read` or `jq`. Large fan-outs should return structured data freely; the parent agent can progressively disclose only the sections it needs instead of paying to re-ingest the full result inline.

## `/workflow` (singular) command

A convenience companion to the plural `/workflows` browser:

| Invocation | Effect |
| --- | --- |
| `/workflow` | Open the same picker as `/workflows`. |
| `/workflow <name>` | Print that workflow's detail (phases, when-to-use, path) directly, no picker. |
| `/workflow new [name]` | Scaffold a starter script in `./.pi/workflows/<slug>.mjs` (valid `meta`, ambient type reference, and `pipeline(items, ...stages)` body). Refuses to overwrite. |

Claude Code ships only the plural browser; the singular verb is a pi extra for
the common direct actions.

## ultracode session mode

`/ultracode [on|off]` (no arg = toggle) ports Claude Code 2.1.156's `ultracode`
effort tier. It lives in pi-workflow because ultracode depends on the Workflow
tool — CC gates it on "workflows enabled" and its standing reminder directs the
model to use the Workflow tool on every substantive task.

When **on**: effort is set to `xhigh` (sticky, restored on off) and a hidden
`isMeta` reminder is injected — full on the enter turn, then sparse every 10
turns (`TURNS_BETWEEN_MAINTENANCE`). When **off**: one "off" reminder, prior
effort restored. Cache-stable (effort held constant; reminders turn-appended and
gated to ~1-in-10 turns). Only active when workflows are enabled.

## `workflow` / `workflows` keyword

Ports Claude Code 2.1.156's per-turn `workflow_keyword_request`. When a prompt
contains the word `workflow` or `workflows`, a hidden `isMeta` message is injected
for that turn with CC's verbatim text:

> The user included the keyword "workflow" or "workflows", which means you should
> use the Workflow tool to fulfill their request.

Same mechanism as the `ultrathink` keyword (prompt injection, no param change,
cache-safe). It lives here — not in pi-thinking-keywords — because the nudge
references the Workflow tool, so it only fires when that tool is registered
(shares the `PI_DISABLE_WORKFLOWS` gate). The matching word is highlighted in the
input by the syntax-input extension. CC's dismissable "Dynamic workflow requested
· … to ignore" TUI affordance is out of scope (input-layer only).
