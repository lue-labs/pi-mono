**Skills:** `autoreview`, `codex-review`, `rusty-review`

**Why they overlap:** All three run code review as a closeout check on local changes or a PR branch. `codex-review` explicitly calls itself a "compatibility wrapper for `rusty-review --engine codex`." `autoreview` describes "Structured code review closeout via Codex (default) or Claude" — which is exactly what `rusty-review --engine codex` does. All three share identical trigger phrases: "Codex review / autoreview / second-model review / after non-trivial edits before commit/ship."

**Recommendation:** Delete `codex-review` (it literally says it's a compat wrapper — the wrapper is the problem). Rename `rusty-review` to just be the canonical review runner; make `autoreview` point to `rusty-review` as a one-liner redirect OR delete `autoreview` too and consolidate into `reviewers`. Currently `reviewers` is the right parent router — `autoreview` is a parallel entry point that causes ambiguity.

**Action:** Delete `codex-review`. Redirect `autoreview` description to "→ use `reviewers` → `rusty-review`" or delete it outright.

## Overlap Findings (ranked by severity)

### 1. CRITICAL — Four memory systems in parallel (dream-memory + pi-memory + letta-shadow + mem0-shadow)

**dream-memory** and **pi-memory** both: extract memories from sessions, persist them, inject recalled memories at session start, schedule consolidation agents. The difference is storage backend (Obsidian markdown wiki vs SQLite) and api generation (dream-memory uses `before_agent_start` for profile injection; pi-memory uses the same hook plus journal). Reading `pi-memory/index.ts` confirms it calls `enqueueDreamConsolidation` — dream-memory's consolidation function is imported inside pi-memory, meaning pi-memory already subsumes dream-memory's consolidation pipeline.

**dream-memory is SOURCE-ONLY** (not in bundle) — it's dead in prod. But pi-memory IS enabled and is the production memory system.

**letta-shadow** and **mem0-shadow** are explicitly labeled as "three-way comparator" experiments (quoting the source: "After 7 days, diff"). They are passive-observer shims that post debrief data to local self-hosted services (Letta on port 8284, mem0 on port 8765). Both are ENABLED in the bundle, meaning they run every session.

**Recommendation:**
- **Dream-memory**: source-only → dead. Check if the obsidian wiki at `~/obsidian/dream-memory/memory/` is still being written; if not, delete. If you want the markdown-wiki format back, pi-memory can be configured to write there. Either way, the source dir is stale — mark for deletion or archive.
- **Letta-shadow + mem0-shadow**: If the 7-day comparison experiment is complete, drop one or both. Running both adds ~2 HTTP POSTs per session to localhost services that may or may not be up. Both silently swallow errors, so the risk is low, but the noise is real. If you've concluded the comparison, drop both (pi-memory is the winner). If the experiment is ongoing, that's intentional.

### 2. HIGH — skill-loader and context-intelligence are the same feature; context-intelligence is a stale tombstone

`context-intelligence/README.md` explicitly says: "Deprecated placeholder. The migrated progressive skill-loading extension now lives at `extensions/skillseek/`." That `skillseek/` dir doesn't exist — the migration landed in **skill-loader** instead (same CC-style progressive skill loading, same `skill` tool, same `&lt;available_skills&gt;` rewrite). `context-intelligence` is a directory with only a README.

**Recommendation:** Delete `extensions/context-intelligence/`. Zero code, clear deprecation notice, replaced by skill-loader.

### 3. HIGH — pi-workflow DUPLICATE (bundle + loose global)

The bundle loads `extensions/pi-workflow/src/index.ts`. The loose globals folder `~/.pi/agent/extensions/pi-workflow/` contains a full copy with the same source. Pi will load both — this is a live duplicate registration of the Workflow tool.

**Recommendation:** Delete `~/.pi/agent/extensions/pi-workflow/` (the loose copy). The bundle version is canonical and versioned.

### 4. HIGH — task-tools vs pi-session-todo (overlapping task-list functionality)

`task-tools` registers `TaskCreate/Get/Update/List` + TUI planning-task pane. `pi-session-todo` registers `TodoWrite` + session-scoped todo TUI pane. Both manage "list of things to do this session." The difference: task-tools is the heavier CC-style planning system (multi-state tasks, main-pane widget); pi-session-todo is a lighter `TodoWrite`-only approach. task-tools is ENABLED; pi-session-todo is SOURCE-ONLY.

The model has two task-management paradigms and may reach for either. Having pi-session-todo source-present but not bundled is a coherent choice IF you're committed to task-tools. But the source sitting there is confusing.

**Recommendation:** If task-tools is the winner, either add pi-session-todo to bundle (intentional addition) or delete its source. Currently it's just noise.

### 5. MEDIUM — context-forking: disabled everywhere but source present

`extensions/context-forking/` has full source. Loose global `context-forking.ts.disabled` is disabled. Not in bundle. This is a `ForkContext` tool that was being experimented with. Unclear if it's planned for future inclusion or abandoned.

**Recommendation:** If not re-enabling, delete or archive. Otherwise add it to the bundle explicitly.

### 6. MEDIUM — tokenjuice source-vs-loose-global split is confusing

The bundle entry for tokenjuice points to `extensions/tokenjuice/index.js` — a 2-line re-export: `import register from "./tokenjuice.generated.js"` which doesn't exist in source. The real bundle is `~/.pi/agent/extensions/tokenjuice.js` (9712 lines). The memory note `tokenjuice-bundle-ahead-of-source.md` documents this: "never regenerate the tokenjuice pi bundle from source (src is behind)." But the bundle JSON still references the extensions source stub, which would fail to load — unless tokenjuice is loaded only from the loose global, not the bundle stub.

**Recommendation:** Clarify the loading path. Either remove tokenjuice from the bundle manifest (since the loose global is the real one) or fix the stub. The current state is a foot-gun if anyone tries to regenerate.

### 7. MEDIUM — usage-soft-cap is source-only + active as loose global — same split issue as tokenjuice

`extensions/usage-soft-cap/index.mjs` exists in source but isn't in the bundle. The live file is `~/.pi/agent/extensions/usage-soft-cap.mjs`. These could have diverged.

**Recommendation:** Either add to bundle and remove loose global, or document that the loose global is canonical.

### 8. LOW — advisor is ENABLED in bundle but hard-disabled in settings

The bundle loads `extensions/advisor/index.ts`. `settings.json` has `"advisor": { "enabled": false }`. The extension checks this config and returns early. So advisor is loaded (costs bundle bytes and a tiny runtime check) but never does anything.

**Recommendation:** Either remove from bundle or accept the dead-weight (the extension gracefully no-ops).

### 9. LOW — openclaw-adaptor, paperclip-cost-forwarder, pi-backpressure are source-only infrastructure

These are real extensions with real source but not in the bundle:
- **openclaw-adaptor**: only useful if OpenClaw is in use; intentionally not bundled by default.
- **paperclip-cost-forwarder**: requires a Paperclip config file; no-ops without it — could be added to bundle safely.
- **pi-backpressure**: TOML-driven gate runner; intentional opt-in (needs a `pi-backpressure.toml` in the project).

These are coherent choices. Low cruft risk.
